# 架构决策记录 (ADR)

## [AD-001] 技术栈选型
- **决策**: 使用 NestJS + Prisma + PostgreSQL。
- **理由**: 类型安全、生产级框架、强大的 ORM 支持。

## [AD-002] 认证机制
- **决策**: 采用 Passport-JWT 策略。
- **理由**: 无状态、易于扩展、标准化的 NestJS 实现方式。

## [AD-003] 统一响应格式
- **决策**: 使用全局拦截器封装返回结构 `{ data: T, statusCode: number }`。

## [AD-004] 异常处理扁平化
- **决策**: 自定义 `HttpExceptionFilter`，确保错误信息以统一的 JSON 格式返回给前端。

## [AD-005] 实时数据库回查
- **决策**: JWT Strategy 在验证载荷后，通过 `usersService` 查询数据库确认用户依然存在且活跃。

## [AD-006] 服务层强制归属权隔离
- **决策**: 在 `Prisma` 查询时，非公开接口强制要求传入 `userId` 过滤条件，防止越权漏洞。

## [AD-007] 文件上传安全约束策略
- **决策**: 在 `ItemsController` 层面使用 `ParseFilePipe`。
- **约束**: 强制限制文件大小（1MB）及 MIME 类型（image/*），在进入 Service 前拦截非法附件。

## [AD-008] 存储桶自动初始化
- **决策**: MinIO 在服务启动时自动检查并创建 `ownd-items` 存储桶。

## [AD-009] 统一物品历史与成本记录表 (Unified Cost Records)
- **决策**: 将物品的“订阅续费 (Renewal)”、“硬件维修 (Maintenance)”以及“组件升级 (Upgrade)”全部统一存储在 `ItemHistory` 表中。
- **理由**: 
    1. **简化统计**：计算物品累计总投入时，只需对该表进行一次 SUM 聚合。
    2. **对齐 UI**：Flutter 端的时间轴节点 (TimelineNode) 本质上就是这些记录的展示。
    3. **可维护性**：统一的 CRUD 接口即可管理所有类型的历史记录，降低系统复杂度。

## [AD-010] API 响应协议以 PRD 为准（统一为 `msg`）
- **决策**: 成功与失败响应统一采用 `{"code": number, "data": any, "msg": string}`。
- **理由**:
  1. PRD 已定义该协议，属于跨端契约，不应漂移。
  2. 前后端统一字段可减少解析分支和错误提示分叉。
  3. 便于后续统计与网关层做标准化日志。

## [AD-011] JWT 校验改为优先按 `sub(id)` 查用户
- **决策**: `JwtStrategy.validate` 优先使用 payload 的 `sub`（用户 ID）查询用户，`email` 仅作为辅助信息。
- **理由**:
  1. 用户主键稳定，不受邮箱变更影响。
  2. 减少“账号字段变更导致 token 失效”的隐性故障。

## [AD-012] MinIO 采用 Fail-Fast 启动策略
- **决策**: MinIO 关键配置缺失时服务启动失败，不再仅记录日志继续运行。
- **理由**:
  1. 对象存储是核心能力，带病启动会把错误延迟到运行期。
  2. Fail-fast 能在开发/部署阶段快速暴露配置问题。

## [AD-013] 迁移采用“结构变更 + 数据回填 + 约束收紧”三步法
- **决策**: 对新增非空字段场景，先允许过渡状态并回填数据，再收紧约束。
- **理由**:
  1. 降低线上迁移失败概率，避免锁表/回滚风险。
  2. 明确迁移脚本的可重复执行与回滚边界。

## [AD-014] 实施流程固定为“四步闭环”
- **决策**: 后续所有任务强制执行“讲解 -> 引导 -> 理解验证 -> AI 测试”。
- **理由**:
  1. 保证知识内化，不把 AI 当纯代码生成器。
  2. 在交付前形成可验证证据链，提升稳定性与可维护性。
